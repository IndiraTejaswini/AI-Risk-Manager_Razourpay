## 1. Point-in-time compliance

Verified by truncation invariance, not by inspection: the matrix is built on the full panel, built again on the panel truncated to `ts < cut`, and the surviving rows are required to be identical. A feature that read data at or after its own timestamp changes when that data is removed.

Cut used: `2018-03-02 23:53:22.800000` (60th percentile of purchase timestamp).

| Scope | Result |
|---|---|
| Full matrix | **PASS** |
| Group `order` | **PASS** |
| Group `customer` | **PASS** |
| Group `pincode` | **PASS** |
| Group `availability` | **PASS** |

Ties are handled explicitly: two orders sharing a timestamp do not see each other. A naive `cumsum().shift(1)` gets this wrong — it lets the second row in a tie block read the first, which is a same-instant read rather than a prior one. `tests/test_golden_fixtures.py` pins the tie case.

**History encodings aggregate `label_a`, not the primary target.** `label_b` is defined by `order_delivered_carrier_date`, and encoding it would make a feature depend on that column transitively. Using `label_a` keeps the invariant absolute: no feature reads the carrier date, directly or transitively. The cost is that the encoding targets a broader outcome than the model predicts; as a predictor that is a larger and better-populated signal, and it carries no coupling to the target's defining column.

**No candidate is excluded on positive count.** The thinnest window (30d) carries 71 positives, 35.5 per parameter, comfortably above the 10 floor. Sample size is not the binding constraint here.

### The constraint that does bind: prevalence drift

The test window the calibration map will be applied to has a prevalence of **0.783%**. The candidates do not match it, and they do not match each other:

| Window | Prevalence | Ratio vs test |
|---:|---:|---:|
| 30d | 0.962% | 1.23x |
| 60d | 1.223% | 1.56x |
| 90d | 1.435% | 1.83x |

Prevalence rises monotonically as the window widens backwards — the failure rate was higher earlier in the panel and declining toward the boundary. The 90d window sits at 1.83x the test base rate; the 30d window at 1.23x.

A 2-parameter Platt map fit at one base rate and applied at another is miscalibrated by construction, and the intercept absorbs most of that mismatch. So the §6 selection is a genuine trade-off rather than a formality: the longer windows buy positives and lose base-rate match, and the Brier-score selection on the validation window is what should adjudicate it. **This report does not pick a window — it states what the choice is between.**

### Degenerate columns

**Zero variance — carries no information as built:**

- `has_zip_prefix` — single value `1` across all 97,658 rows.

A constant column cannot produce a split, so it costs nothing at training time and contributes nothing. It is left in rather than dropped because it is part of the production availability contract and becomes informative the moment a source can be absent; on Olist that source never is. Flagged here so it is a known no-op rather than an assumed signal.

**At least 95% null** — `cust_prior_avg_value`, `cust_days_since_prior_order`, `cust_prior_boleto_ratio`. See the customer-history note below; these are not defects, they are the repeat-purchase rate.

### What the null rates say

**Customer history is almost entirely empty.** 94,734 of 97,658 orders (97.01%) have no prior order from the same customer, so every expanding-window feature is null or zero for them. That is Olist's ~3% repeat-purchase rate showing up exactly where ARCHITECTURE.md §5.4 predicted it would, and it is the same fact that made the TabPFN cold-start router unevaluable. The customer group is built, PIT-correct, and carries almost no signal on this dataset. It is retained because the production feature contract includes it and because the smoothed encoding degrades gracefully to the global prior — not because it is expected to contribute here.

**Pincode history is the group that actually populates.** Every order has a zip prefix, and the panel is dense enough that the smoothed target encoding has real observations behind it for most rows. ARCHITECTURE.md §4.5 expects this to outrank the address-string features, and on Olist it is the only history-derived signal with enough coverage to matter.

Smoothing constants: pincode `m=50`, customer `m=20` pseudo-observations at the running global rate. Strong by design — a pincode with a handful of prior orders cannot take an extreme value, which is what stops the encoding degenerating into a blanket blacklist (§4.5, §10).
