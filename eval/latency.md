### Why feature construction still costs what it does

### Two changes, not one

The 3250ms figure below is step 7's, before the history store existed. There is an intermediate state worth recording, because the second change was not made for latency at all.

| Implementation | Total p50 | Verdict |
|---|---:|---|
| Step 7 — re-derive from 97k rows per request | 3250.0ms | FAIL |
| Store, summing each group's slice per query | 334.2ms | FAIL |
| Store, per-group cumulative sums precomputed | 61.3ms | PASS |

The third row came out of a **correctness** fix. The index summed a group's slice at query time with NumPy's pairwise summation while the batch row-scan accumulated it sequentially through pandas; the two disagree in the last bits once a group is large, and the startup self-check caught it (`eval/feature_expansion.md` §3.2). Precomputing the same per-group cumulative sum the scan computes makes the two bit-identical **and** turns an O(prior rows) query into an O(1) lookup. The speedup is a side effect of making the two paths agree, which is worth stating plainly: it was not a latency optimisation and it was not tuned for.

Step 7 measured 3250ms here, of which 3216ms was feature construction: every request re-derived the point-in-time aggregates from the whole history. That is now 56ms.

| | Step 7 | Now | Change |
|---|---:|---:|---:|
| Feature construction p50 | 3216.5ms | 56.3ms | 57.2x faster |
| Total p50 | 3250.0ms | 61.3ms | 53.0x faster |

What changed is **how the prior window is evaluated, not what it means**. A `HistoryStore` built at startup indexes the historical population by group and timestamp; a query binary-searches it instead of scanning 97k rows. The feature formulas are untouched, and `features/store.py` sets out why that is one definition with two evaluation strategies rather than a second implementation.

Two checks keep it honest, and both are structural rather than incidental:

- **At startup**, the service scores **every** order in the historical population through the store and requires all 35 features to be bit-identical to the row-scan — not a sample. A fixed 40-order stride used to stand in for this and passed on two genuinely defective implementations, because neither defect's rows intersected the stride (`eval/feature_expansion.md` §3.2 and §5 below). A drift would not raise anywhere else — the model would happily score the wrong number — so the service refuses to start rather than serve.
- **In the test suite**, the API-vs-batch parity assertion still requires 1e-12 agreement with the batch predictions, and still passes.

Getting there also required fixing a real precision bug: a single prefix-sum across the whole index accumulates across group boundaries, so a small group's sum became the difference of two large numbers and disagreed with the row-scan by 3.4e-10. Grouped indexes now sum the slice directly — the same elements, added in the same order as the scan — and only the single-group global index keeps a prefix array, where the accumulation order is identical by construction.

### The remaining long pole

Feature construction is still 92% of the request, and it is **no longer algorithmic**. The store answers each prior-window query in microseconds; what remains is pandas overhead on the per-request frame: constructing small DataFrames, factorising string keys to attach the customer and product lookups, and materialising ~35 columns one at a time. It is fixed cost per call, not work that scales with the history.

That is a different problem from the one Step 7 had. It is fixed cost, not algorithmic cost, so a further speedup would be an optimisation with no deadline attached, against a layer the API-vs-batch parity guarantee rests on. Not attempted, and not needed to clear the budget.

**The verdict: this meets the 200ms budget**, worst-pass p50 61.7ms. The improvement from the 3250ms starting point came from the correctness fix above — precomputing the store's per-group cumulative sums so the two evaluation strategies agree — not from optimising this layer or from dropping the SHAP reasons, which are still computed and still in every response.

## 3. Cold start

**10.8 seconds** from process start to the first request being servable, of which the full-population store self-check (97,658 orders, every row) is 5.9s (54%). Widening that check from a 40-order stride to every row (§5) added roughly that much; the fix that made the check possible to widen also made the batch feature build itself faster, which is most of why total cold start moved only slightly.

It belongs on its own line rather than inside p50 because a judge running `docker run` experiences it once and every request after that never pays it again. Averaging it into a per-request figure would understate the wait they actually see and overstate the steady-state cost.

| Startup stage | What it does |
|---|---|
| Source tables | Four CSVs read and cached |
| Feature matrix | Full-panel build, needed to fit the model |
| Model | LightGBM train to the early-stopping round |
| Calibrator | Platt on the 30-day window |
| SHAP explainer | Built once (§8: cached at startup) |
| History store | Prior-window index over the historical population |
| Store self-check | Store vs row-scan on every order, all 35 features |

The model is **trained** at startup rather than loaded from an artifact. That is the honest description of this build: `artifacts/models/` holds a saved booster but the service does not read it, so the container needs the dataset. A production image would ship the fitted artifacts and load them, which removes the training and the full-panel feature build from cold start and leaves the store build — the largest remaining piece is then the index, not the fit.

## What was measured

Single process, warm caches, in-process calls to the same `ScoringService` the FastAPI app holds — HTTP framing and network are excluded, so these numbers are a floor rather than an end-to-end figure. Startup cost is excluded from the per-request figures because it is paid once at process start; it is reported above so a container's readiness delay is not a surprise.

`pincode lookup` does not appear as a stage: it is not a separate call here. The pincode encoding is a point-in-time aggregate computed inside feature construction, and `pgeocode` geo features (§4.5) are not built.
